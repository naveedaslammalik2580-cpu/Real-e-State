## Phase B — C-1 deterministic workspace selection (commit `c16e33d`)

### Important schema discovery (changes the risk picture, not the fix)
T2a enforces **one ACTIVE membership per user** via the partial unique index `workspace_members_one_active_per_user` on `(user_id) WHERE status = 'active'`, and T3's invitation acceptance removes the previous active membership before activating a new one. **Two active memberships are therefore impossible in production today** — both October audits missed this index. C-1 is a *latent* defect: the bare `LIMIT 1` picks are non-deterministic only if that constraint is ever relaxed (e.g. true multi-team support). The fix was still applied, as defense-in-depth with an explicit, total rule — and the migration/rollback headers record the discovery so nobody over- or under-states the risk later.

### The rule (identical at every site)
```sql
ORDER BY (CASE WHEN w.owner_user_id = <user> THEN 0 ELSE 1 END), w.created_at, w.id
```
joined to `public.workspaces` — **owned workspace first** (matches `ensure_personal_workspace`'s own provisioning intent and the personal-workspace model), **then earliest `workspaces.created_at`** (the personal workspace is provisioned at signup, so it is also the earliest in the normal case), **then workspace id** — guaranteeing a total order with no possible ties. Only the membership-selection subquery changed in each function: names, signatures, return types, `SECURITY DEFINER`, `set search_path = ''`, grants, and comments are preserved verbatim. The second `LIMIT 1` inside the set/reset-permissions RPCs is an audit-log name lookup scoped to the already-selected workspace — not a selection — and was deliberately left untouched.

### Scope correction vs the audit
The audit named 5 functions. Grepping the full migration chain for bare `LIMIT 1` over `workspace_members` found **11 functions across 7 migrations**, and fixing only the 5 named ones would have left the resolvers disagreeing with each other (the exact inconsistency C-1 is about). All 11 were redefined: `authz.my_workspace_id`, `authz.my_team_member_id`, `authz.my_role`, `automation_internal.ensure_personal_workspace`, `automation_internal.workspace_of`, `public.realtoros_my_permissions`, `public.realtoros_set_role_permissions`, `public.realtoros_set_member_permissions`, `public.realtoros_reset_member_permissions`, `public.realtoros_register_push_subscription`, `public.realtoros_set_notification_preferences`.

### Regression test design (adapted to the real schema)
A literal "two ACTIVE memberships" fixture **cannot be inserted** — the unique index rejects it (the test asserts this: the constraint still holds). The test therefore verifies determinism at the strongest level the schema allows: users with one ACTIVE membership plus soft-deleted / invited / left memberships in *other* workspaces (including workspaces they own), asserting `ensure_personal_workspace`, `my_workspace_id`, `my_team_member_id`, `my_role`, and `realtoros_my_permissions` all agree on the same workspace across repeated calls, that an owned workspace wins for the provisioning function, that the resolvers agree with each other for a non-owner member, and that ordinary single-user provisioning is unchanged. **5/5 pass.** (If the one-active constraint is ever relaxed, this test should be extended with a true two-active fixture.)
